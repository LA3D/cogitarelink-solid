# Rung 1.5 Redesigned — L1/L2/L3 Engineering Evaluation

**Date**: 2026-05-23
**Status**: Design (supersedes the v2 matrix at `docs/plans/2026-05-15-rung-1-5-eval-matrix.md` and the session-handoff at `docs/plans/2026-05-15-rung-1-5-session-handoff.md`)
**Decision anchor**: D102 repo / D97 vault (to be ratified on accepting this design)
**Canonical L2 source**: `~/Obsidian/obsidian/03 - Resources/Agentic Memory Systems/Core Concepts/Memory Substrate vs Memory Profile.md`
**Intended consumer**: the engineering session that runs Phase A. Not an academic deliverable.

---

## 1. What changed

The previous Rung 1.5 design framed the evaluation as a measurable *claim* — Tier-2 Pod (with affordance descriptors) reduces harness cost vs Tier-1 brute-force vs filesystem baseline, on a fixed task suite. Three conditions (B1 / B2 / T). One Pod harness skill. Success = T condition wins on tokens and quality.

That framing made sense when wiki-memory L3 was still being designed. It no longer fits:

- **Filesystem isn't a baseline** — it's a non-option. The choice of substrate is settled (Pod-as-architecture, web service, multi-machine, shareable). Comparing the chosen substrate to a substrate we've ruled out doesn't help us design the Pod.
- **The Pod harness is no longer one skill** — it's a suite (solid-addressbook, solid-wiki-memory-l3, solid-owner-identity, wiki-search, 6 action skills, 3 inbox skills, with more coming). The T condition collapsed into "agent equipped with skill X" — a different measurement per skill.
- **Wiki-memory L3 itself is no longer a hypothesis** — three traditions converge on substantively the same substrate (Karpathy/Ghumare/AKBP, ByteRover/xMemory/Hindsight, Hermes/Supermemory). The eight-shape catalog ships. We stipulate L3 is good and ask how well agents *use* it.
- **L2 has been treated as axiomatic** but never measured. The canonical L2 doc explicitly poses the eval question: *"can L2 carry an arbitrary L3?"* and defers operational details (validation algorithms, scoring formulas, detection thresholds) to "Rung 1.5+ evaluation." That deferral is what this redesign cashes in.
- **L1 agentic behavior is untested** — Solid Pod conformance is W3C-tested; whether agents reach for the standard discovery / auth / federation mechanisms when appropriate is not.
- **Multi-Pod federation is the next engineering question** and it has nowhere to land in the old design.
- **The wiki-memory compounding claim is a round-trip, not a single direction.** Karpathy's gist names three operations — Ingest, Query, Lint — and the value proposition is that the wiki *compounds* over time rather than accumulates. Retrieval-only evaluation can't observe compounding. Creation-only evaluation can't observe whether the creation produced retrievable content. The round-trip is the actual measurement.

The redesign reframes Rung 1.5 from "prove a claim" to "instrument the substrate so we can engineer it." The artifact is not a paper. The artifact is a Pod design that demonstrably works.

## 2. What we stipulate (not under test)

- **Pod-as-substrate**: settled. Filesystem can't share across machines or attach multiple agentic harnesses; web service is the answer.
- **Wiki-memory L3 as the canonical memory profile**: stipulated good based on the three-tradition convergence. The eight-shape catalog (PageShape + ThingShape + ConceptShape + PersonShape + PlaceShape + EventShape + OrganizationShape + HowToShape) is settled per D98.
- **Skills + structured memory are both required**: prior back-of-the-envelope tests in `~/Obsidian/obsidian/retrieve-workspace/iteration-1/` show meaningful with-skill vs without-skill deltas on a non-trivial L3 (the vault). We don't need to re-prove that skills help; we need to learn *which* skill designs and *which* substrate features earn their keep.

## 3. What we want to learn

Engineering questions, organized by which layer the finding implicates. A finding can implicate one layer or several; the eval's job is to make that attribution visible.

### 3.1 L1 — Solid Pod (agentic behavior on universal substrate)

L1 conformance is W3C-tested. What we don't know is whether agents *use* L1 features when they should. Each question below has a yes/no observable behavior in agent trajectories.

| L1 question | Observable in trajectory |
|---|---|
| Does the agent find `.well-known/solid` on cold arrival? | First requests to a fresh Pod |
| Does it follow `solid:storageDescription` Link headers? | Header-following step |
| Does it use Solid-OIDC + DPoP when auth-required, or treat 401 as a wall? | Auth retry behavior |
| Does it discover via Link headers, or fall back to URL-guessing? | Trajectory of intermediate GETs |
| Does it use Memento `Accept-Datetime` for temporal queries when relevant? | Header negotiation step |
| Does it read LDN inbox / Solid Notifications when present? | Inbox-discovery step |
| At multi-Pod: does it cross Pods via dereferencing, or assume single-Pod scope? | Cross-Pod GETs |

L1 findings translate to: "the Solid Pod gives agents X feature, and they ignore it" → either improve substrate self-description, or accept that the feature is YAGNI for agentic use.

### 3.2 L2 — Memory substrate (the seven invariants as testable hypotheses)

From `Memory Substrate vs Memory Profile.md` (vault). Each invariant becomes an observable behavior under stress; wiki-memory L3 is the specific instance being measured.

| # | L2 invariant | What an agent should do if the invariant holds | Wiki-memory L3 mechanism (and its current gap) |
|---|---|---|---|
| 1 | Bounded branching with typed containment | Traverse from a hub without overload; pageinate or summarize fan-out | **No structural mechanism**; Fano-bound is discipline-only. Eval surfaces whether hubs overload agents. |
| 2 | Tiered / progressive retrieval | Use synthesis page → container → page hierarchy rather than enumerate every container | Tier handles exist (D55 + synthesis page D93); discoverability of the hierarchy is the open question. |
| 3 | Lifecycle metadata as first-class | Use temporal info (Memento, dct:created, maturity) when relevant | PROV-O, Memento, two-stage commit shipped; scoring algorithm TBD. Eval asks whether agents *use* these. |
| 4 | Explicit write + implicit signals | React to MemTrigger events (BoundExceeded, ContradictionDetected); distinguish own writes from substrate-inferred state | MemTrigger detector wiring shipped D101; delivery is A+C (post-write LDN GET + Solid Notifications). Atomic Pattern B deferred per RQ-Atomic-Feedback-1. |
| 5 | Hybrid blob + graph storage | Use both layers — read body for prose, query .meta for relationships | Dual-layer linking shipped (D58/D71/D81). Agent fallback to one side = signal the projection isn't earning its keep at the agent layer. |
| 6 | Separable procedural memory | Recognize when to consult a skill vs read a memory note; not confuse the two | Skills are the procedural layer. skill-creator harness with-skill vs without-skill measures this directly. |
| 7 | Out-of-domain honesty | Decline confidently when the Pod doesn't have the requested content; not hallucinate | `/wiki/working/` permissive shape (D73) is the place to put OOD items; detection algorithm is **TBD**. Likely the highest-risk invariant. |

The eval's job at L2 is *attribution*. When an agent succeeds or fails, was it because of a specific invariant? Which invariants are load-bearing under stress, which are decorative, and which break first under scale?

L2 findings translate to: "the L2 invariants are *necessary and sufficient*" (validation), or "invariant N broke and the substrate had no mechanism to enforce it" (gap → either add a mechanism or revise the invariant set).

### 3.3 L3 — Wiki-memory profile (instance-specific questions)

L3 is stipulated good *as a design*. What we don't know is which of its specific features agents reach for in practice.

| L3 question | Observable |
|---|---|
| Which affordances in `/vault/meta/affordances/` get used vs ignored? | Affordance-catalog reads + which descriptors get followed |
| Does Type Index dispatch get used, or do agents skip it for direct container enumeration? | Type Index GETs vs container listings |
| Do agents use class-based SHACL targeting correctly when creating content? | SHACL pass/fail rate + which shape gets matched |
| Do agents respect the two-stage commit pattern (`/working/` → durable container) or skip straight to durable writes? | POST targets |
| Are the 8 shapes (Page + Thing + 7 typed) discoverable cold? | Schema-reading step before creation |
| Does the synthesis page (D93) actually serve as the entry point, or do agents bypass it? | First reads on cold arrival |
| Do agents respect two-stage commit (`/working/` → durable container) or skip straight to durable writes? | POST targets during creation |

L3 findings translate to: "feature X is YAGNI" (no agent uses it across N tasks → candidate for removal), or "feature X is misused" (agents reach but use wrong → better self-description needed), or "feature X is correctly used" (validates the design).

### 3.4 Karpathy's three operations (the L3 question frame for creation)

Karpathy's [Agentic Wiki Design Document](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) makes three operations explicit, and the L3 profile inherits them:

| Karpathy operation | What it does | L3 mechanism | What we observe |
|---|---|---|---|
| **Ingest** | One source → fan-out to N page updates + log entry. The compounding moment. | Body-affordance projection (D58/D71) + Type Index dispatch (D78) + two-stage commit (D73) + log container | Did fan-out happen (N existing pages updated), or did the agent dump everything into one new page (accumulation, not compounding)? |
| **Query (with file-back)** | Synthesize answer; valuable parts file back as new wiki pages. Queries become knowledge. | Backlinks affordance (D45) + working-memory write + crystallize | Did the agent file the answer back? Is it later retrievable by a fresh-context query? |
| **Lint** | First-class audit: contradictions, staleness, orphans. | `mem:*` trigger vocabulary (D74): `mem:ContradictionDetected`, `mem:BoundExceeded`, `mem:ConsolidationSuggested`, `mem:ReflectionDue`, `mem:OODQuerySignal` | Does the substrate emit the triggers? Does a lint-equipped agent act on them? |

These three are the operations that test L2 invariants in *combination*, not in isolation. Ingest stresses 1, 3, 4, 5. Query-with-file-back stresses 2, 4, 7 plus the compounding round-trip. Lint stresses 1, 3, 7 plus the substrate-trigger half of invariant 4.

A finding like "agent ingested without fan-out" is not an L3 retrieval question — it's a compounding-claim failure, and it implicates either substrate self-description (agent didn't know to update existing pages) or skill design (skill didn't tell it to). The eval observes which.

### 3.5 Multi-Pod (federation — was Phase D ablation)

Federation surfaces L1+L2 questions that single-Pod evaluation can't reach.

| Federation question | Observable |
|---|---|
| Discovery — does the agent find a second Pod, or assume single-Pod scope? | Cross-domain GETs |
| Cross-Pod queries — does it dereference across Pods, or attempt a federated query at one endpoint? | SPARQL FROM clauses, cross-domain HTTP |
| Identity — does the agent use the same WebID across Pods, or treat each Pod as an isolated session? | OIDC reuse |
| Cross-Pod indexing — is there a discovery surface, or does the agent enumerate? | Any cross-Pod registry use, or evidence of its absence |
| L3 mismatch — when two Pods share L2 but use different L3 profiles, does the agent map between them? | Vocabulary translation steps |

This is the question RQ-Substrate-4 in the canonical L2 doc names explicitly. Phase D is where it gets operationalized.

## 4. Eval harness — skill-creator + trajectory + behavior judge

### 4.1 Substrate

skill-creator's harness is the foundation:

- Spawns fresh-context subagents (closest we can get to cold-start measurement in Claude Code)
- with-skill vs without-skill comparison is structurally appropriate for L2 invariant 6 (separable procedural memory) and most L3 questions
- Auto-aggregates tokens / duration / per-assertion pass-fail
- Eval-viewer for qualitative review

What it doesn't natively give us, and what we add:

### 4.2 Trajectory capture (revised 2026-05-23 — use Claude Code's persisted JSONL)

**Replaces the original subagent self-logging plan.** Claude Code persists the full trajectory of every Agent-tool-spawned subagent as JSONL at:

```
~/.claude/projects/<project-slug>/<parent-session-uuid>/subagents/agent-<hash>.jsonl
```

Plus an `agent-<hash>.meta.json` sidecar with `{agentType, description, toolUseId}`. The path was confirmed end-to-end during the Phase A pilot setup (see auto-memory `subagent-trajectories`).

Discovery pattern from the spawning agent: grep meta.json files for the subagent's `description` to find the hash, then copy/read the corresponding `agent-<hash>.jsonl`.

**Format**: each line is one turn. Block types appearing in `message.content[]`:

- **`text`** — assistant's visible narration ("Now I'll check the affordance catalog...", "Found 1 match"). This is the form of chain-of-thought that subagents make externally visible. Adequate signal for retrieval-style behavior judging.
- **`tool_use`** — every tool invocation with full input payload.
- **`tool_result`** — every result (including errors).

**Known gap: extended-thinking blocks are NOT in subagent trajectories when spawned via Claude Code's in-process Agent tool.** Verified across 9 subagent runs in the Phase A pilot session (4 eval + 4 judge + 1 research; general-purpose and claude-code-guide types): `type: "thinking"` block count = 0 in every JSONL. The in-process Agent tool used from within Claude Code does not expose a `thinking` parameter, and the built-in `general-purpose` and `claude-code-guide` agent types ship without extended thinking enabled.

Extended thinking **is** supported by the underlying mechanism, just not via the path we're using:

- **Claude Agent SDK** (TypeScript + Python `AgentDefinition`) accepts a `thinking: {type: 'enabled' | 'adaptive' | 'disabled', budget_tokens: int, display: 'summarized'}` field per custom agent definition. Subagents spawned via the SDK with thinking enabled emit `type: "thinking"` blocks into the trajectory.
- **Custom agent definitions** at `~/.claude/agents/<name>.md` could (per spec) embed thinking configuration in their frontmatter, but this user has no custom agents installed; built-in agent types can't be modified.
- The in-Claude-Code `Agent` tool I'm using doesn't expose a per-call thinking parameter — agent-type config determines the behavior.

Implications:

- For Phase A (retrieval-style tasks) the text + tool_use + tool_result signal is adequate — the judge correctly attributed skill-shortcut vs cold-discovery behavior from text blocks alone during the pilot.
- For Phase B+ (creation, lint, federation) where *why* an agent did something matters more than *what* it did, this is a deeper gap. We can observe that an agent reached for affordance X but not necessarily why it ruled out Y.
- **Mitigation paths** (in priority order):
  1. **Define a custom `eval-runner` agent** at `~/.claude/agents/eval-runner.md` with `thinking: {type: 'enabled', budget_tokens: 10000-20000}` in its frontmatter; spawn Phase B+ eval subagents with `subagent_type: "eval-runner"` instead of `general-purpose`. Cheapest path; should land before Phase B kickoff.
  2. **Spawn via the Agent SDK programmatically** — write a small Python harness that calls `AgentDefinition(thinking={"type": "enabled", "budget_tokens": 15000})` and reads the persisted JSONL after completion. More setup but gives finer-grained control; preferable if mitigation 1 turns out to be insufficient.
  3. **Prompt-level reasoning elicitation** — instruct the subagent to explain its choice before each tool call. Cheapest of all, but turns reasoning into self-report (the very thing we moved away from). Use only if 1 and 2 fail.
  4. **Phoenix/OTEL trace capture** — external observability substrate. Highest setup cost, comes back if all above prove insufficient.

The eval proceeds with text-block signal for Phase A (sufficient). Mitigation 1 (custom agent definition) gets investigated and likely landed before Phase B kicks off, so Phase B+ trajectories include thinking. The path is now concrete — this is a documented gap with a known solution, not an open question.

### 4.3 Behavior judge (separate from output grader)

skill-creator's built-in grader scores **outputs** against assertions. We add a **behavior judge** scoring trajectories. The judge reads `trajectory.jsonl` and emits `behavior_grading.json` with assertions like:

- "Agent discovered storage description before any container enumeration" (L1)
- "Agent read affordance catalog at least once" (L3)
- "Agent followed Type Index dispatch (didn't skip to direct container listing)" (L3)
- "Agent traversed hub node without overload" (L2 invariant 1)
- "Agent used Memento Accept-Datetime when task required temporal context" (L2 invariant 3 + L1)
- "Agent declined when Pod lacked content (didn't hallucinate)" (L2 invariant 7)
- "Agent used both body and .meta layers" (L2 invariant 5)

Each assertion attributes to one or more L-layers. The aggregator rolls up per-layer pass rates so a phase report tells us: "at this scale, L1 utilization X%, L2 invariant 1 broke in N/M trajectories, L3 affordance Y used in P/M."

### 4.4 Outcome metrics retained, demoted to secondary

skill-creator's native metrics (tokens, duration, output-assertion pass rate) stay. They're how we triangulate behavior judgments. But they're not the headline — behavior is.

### 4.5 Round-trip consistency (third measurement axis)

For phases that test creation (B1, B2) and federation (D), every creation task is paired with a corresponding retrieval task. The retrieval runs after the creation completes, with fresh context, and must find what the creation produced via the L3's declared affordances. The pair passes only if both halves pass *and* the retrieval finds the created content.

Workspace layout: paired tasks are stored as `eval-NNN-create/` and `eval-NNN-retrieve/`. The aggregator emits round-trip pass-rate alongside per-task pass-rate.

A creation task that passes its output assertions but fails its round-trip retrieval is the most diagnostic single finding the eval can produce. It means the creation produced content the substrate's read-side affordances can't reach — a **mismatch between create-side and read-side affordance design**, not an agent failure. Distinguishing this from agent-quality failures is what this axis is for. It is also the direct measurement of wiki-memory's *compounding* claim: a wiki that compounds is one where what you write today is findable next week, by a different agent, via the L3's normal navigation.

The axis extends naturally to multi-Pod (Phase D): create on Pod A, retrieve from Pod B (different agent, possibly different L3 profile). Same pass/fail semantics; new failure modes (cross-Pod discovery, identity, vocabulary mapping).

## 5. Phase sequence (evolve based on observation)

Each phase produces an engineering deliverable (design implications), not a claim. **The sequence is intentional**: Phase C (scale extension) runs *before* the B1/B2 split because "creation at appropriate scale" looks different from "creation at current scale." The current B1/B2 subdivision is the best guess we can make today; expect it to evolve as A and C surface specific behavioral patterns. **Treat the subdivision as provisional, the sequence as committed.**

**Sequence**: A pilot → A full → C → B1 → (build lint skill if surfaced) → B2 → D.

### Phase A — Affordance utilization, retrieval, single Pod, current scale

- **Skill**: wiki-search first. Narrow scope, fast harness shakedown.
- **Tasks**: 4–6 prompts exercising cold-start arrival + literal-substring search + paged retrieval + AND-queries against the current Pod content (~dozens of wiki-memory L3 pages).
- **Conditions**: with-skill (solid-pod wiki-search) vs without-skill (Solid spec + Pod self-description only).
- **What we'll learn**:
  - L1: do agents find storage description / affordance catalog cold?
  - L3: do agents use the `?ext=search-grep` affordance descriptor or fall back to enumerate-and-grep?
  - L2 invariant 6: is the with-skill delta meaningful at this scale?
- **Deliverable**: ranked list of which L1/L3 affordances were used vs ignored, plus failure-mode notes for the design redesign loop.

### Phase C — Scale extension (run before splitting Phase B)

The substrate at current scale (~dozens of notes) under-tests every L2 invariant that's about behavior under load — bounded branching, tiered retrieval, OOD honesty. Running scale extension before creation evaluation is intentional: it tells us what "creation at appropriate scale" needs to optimize for, which informs how Phase B should be subdivided.

- **Substrate**: same Pod, expanded content. Two options:
  - **Vault import** (preferred): import a non-trivial subset of the Obsidian vault as wiki-memory L3 content. Real semantic diversity, real hub/dead-end distribution. Side-benefit: the import itself is a creation-at-scale exercise that gives us free observations for Phase B design.
  - **Synthetic expansion**: programmatically scale to ~1k or ~10k notes preserving the typed-edge structure. Faster but artificially clusters.
- **Tasks**: rerun Phase A retrieval tasks at expanded scale; the shape of the cost curve is the headline output.
- **What we'll learn**:
  - L2 invariant 1: which features become load-bearing at scale (Fano-bound visible? hub-overload?)
  - L2 invariant 2: does tiered retrieval get used more at scale (correlation with task quality)?
  - L2 invariant 7: does the agent's OOD honesty degrade at scale (more content → more spurious "matches" → more confident wrong answers)?
  - The shape of the cost curve — sub-linear, linear, super-linear in corpus size?
- **Deliverable**: which substrate features are scale-load-bearing vs YAGNI-at-scale; whether the substrate needs hub-paging or summarization affordances; **input to Phase B design** (what creation needs to produce for retrieval to work at scale).

### Phase B1 — Karpathy operations 1 + 2 (Ingest + Query-with-file-back), single Pod, informed scale

Reframed from the prior "Phase B creation tasks." Per Karpathy's gist (§3.4 above), wiki-memory has three operations and the compounding claim only manifests across them as round-trips. B1 covers the two operations runnable against the existing skill suite.

- **Skills**: solid-addressbook, solid-wiki-memory-l3 (Person creation path), plus wiki-search for the retrieval half of the round-trip.
- **Tasks** (each is a paired creation + retrieval, per §4.5):
  - **B1-Ingest**: Agent processes a new source (a paper abstract, a transcript snippet). Must update existing wiki pages with new cross-references **AND** create entity pages **AND** log the ingest. Round-trip verification: a follow-up retrieval task (fresh context) finds both the updated existing pages and the new entity pages by typed-edge traversal.
  - **B1-Query-with-file-back**: Agent answers a substantive question; valuable parts of the answer file back as new wiki pages (per Karpathy: "queries become knowledge"). Round-trip verification: re-query later (fresh context) surfaces the filed-back content.
- **Conditions**: with-skill vs without-skill, plus round-trip consistency as the diagnostic axis.
- **What we'll learn**:
  - L3: is the eight-shape catalog discoverable cold during creation? Does Type Index dispatch happen?
  - L2 invariant 4: do agents respect two-stage commit (working-memory → crystallize), or skip straight to durable writes?
  - L2 invariant 7: when ingesting underspecified input, do agents decline or fabricate?
  - **Compounding observation**: does the fan-out actually happen (ingest updates N existing pages), or does the agent dump everything into one page (accumulation, not compounding)? This is the central wiki-memory claim, observed directly.
  - **Round-trip findings**: which create-side affordances produce content that's read-side findable, and which produce content the substrate can't surface back.
- **Deliverable**: ranked list of creation affordances by round-trip pass rate; specific failure modes on the create-read mismatch; a refined understanding of how to subdivide B1 further (or merge B2 into it) for the next iteration.

### Phase B2 — Karpathy operation 3 (Lint), gated on lint skill

Karpathy's third operation is the sharpest claim in his gist: lint is first-class, includes *semantic* contradiction detection, and is what keeps the wiki compounding rather than degrading. Wiki-memory L3 supplies the substrate side via the `mem:*` trigger vocabulary (D74). What's missing is the agent-side skill that consumes and acts on these triggers — the Pod analogue of vault `/audit` + `/curator` + `/review-note`.

- **Prerequisite**: a Pod-side lint/curator skill. Not yet built. Tracked as task #10.
- **Trigger to build**: Phase A or C surfacing failure modes that lint would catch (orphan creations, ignored contradiction signals, hub overload at scale). Don't build prophylactically; let the eval surface what the skill needs to do.
- **Tasks** (once skill exists, all round-trip paired):
  - **B2-Contradiction**: Plant a contradiction (agent A claims X, agent B claims ¬X in separate writes). Does the substrate emit `mem:ContradictionDetected`? Does a lint-skill-equipped agent C find and reconcile? Round-trip: does a subsequent query return a consistent answer?
  - **B2-Orphan**: Create an orphan resource (no incoming typed edges). Does the agent detect and integrate it during a lint pass? Round-trip: is the orphan reachable by graph traversal after lint?
  - **B2-Bound**: Create N+1 children in a container nominally bounded at N. Does `mem:BoundExceeded` fire? Does the agent react (split, summarize, paginate)?
- **What we'll learn**:
  - Does the substrate's trigger vocabulary deliver actionable signals?
  - Does a lint-skilled agent improve substrate hygiene over a no-skill baseline?
  - Is N=3 (or N=12 per the Fano bound) the right hub threshold (RQ-Hub-1)?
  - The full compounding claim: lint is what prevents compounding from collapsing into accumulation. Without lint, every ingest pushes the wiki closer to incoherence. With lint, the wiki stays navigable.

### Phase D — Multi-Pod federation

- **Substrate**: a second Pod, collaborator-flavored content (a fixture for the eval, not real collaborator data).
- **Tasks**: cross-Pod discovery, cross-Pod queries, cross-Pod identity, cross-Pod indexing — each paired round-trip across Pods (create on A, retrieve from B).
- **Conditions**: with-skill vs without-skill. The skill question is bigger here — a federation skill may need to be built before Phase D runs, similar to B2's lint skill prerequisite.
- **What we'll learn**:
  - L1: does Solid's federation story work for agents in practice?
  - L2 invariant 5: does hybrid storage survive federation, or do dual-layer assumptions break across Pods?
  - The cross-Pod round-trip: content created on Pod A, does it get retrieved from Pod B via L3 traversal — or does the agent have to know which Pod owns what?
  - RQ-Substrate-4: when Pods share L2 but differ in L3, what cross-profile mapping is required?
- **Deliverable**: federation design — what new affordances are needed, what existing affordances need to be cross-Pod aware, what an "agent-cross-Pod" identity story looks like, whether there's a separable cross-Pod indexing concern.

## 6. What the eval deliberately does NOT settle

- **Not a paper**. The artifact is engineering knowledge, not publishable claims.
- **Not L1 spec conformance**. W3C tested that. We test L1 *agentic behavior*.
- **Not "wiki-memory L3 vs other L3 profiles"**. Single profile under test; alternatives are mentioned in the L2 doc but evaluation of them is out of scope until another L3 profile actually ships.
- **Not feature ablation as a primary axis**. Stripping individual features one at a time is an interesting follow-on if behavior judgments don't reveal which features matter — but the prior is that affordance utilization signals are richer than ablation deltas.

## 8. Decision strategy — pilot first, then evolve

The prior session-handoff weighed Strategy A (build all prereqs then run) vs Strategy B (minimum viable pilot). Strategy B is the path, with an extension: **pilot first, then evolve the phase structure based on what each phase surfaces.** The B1/B2 split in §5 is the current best guess; expect it to shift after Phase A and Phase C produce real data on agentic behavior.

The principle: don't lock in a multi-phase eval plan that can't absorb learning. Phase A pilot → Phase A full → Phase C (scale) is the committed sequence. Phase B's subdivision into B1 (Ingest + Query-with-file-back, runnable) and B2 (Lint, gated on lint skill) is provisional and will be refined when Phase C's deliverable lands.

This is consistent with the engineering framing in §1: the eval is a design instrument, not a proof. If the structure of B needs to change because A and C taught us something, that's the instrument working — not a problem.

## 9. Pilot specification (immediate next step, not part of this doc's commitments)

When the pilot session opens:

- Single skill: `wiki-search` from the sibling `solid-agent-skills` repo.
- 2 task prompts initially: one literal-substring find ("find pages mentioning *progressive disclosure*"), one paged-retrieval ("find all pages mentioning *Memento*, return up to 20").
- Configurations: with-skill (skill loaded) + without-skill (no skill, agent given only Pod URL).
- Trajectory capture: subagent self-logs to `trajectory.jsonl`.
- Behavior judge: a separate grader subagent reading the trajectory and producing 6–8 assertions across L1 / L3 / L2-invariant-6 categories.
- Workspace: `eval-workspace/pilot-wiki-search/iteration-1/` per skill-creator conventions.

Decision criterion: if both agents complete both tasks and the trajectory + behavior judge produce useful signal, Phase A proceeds with the full task suite. Otherwise the harness gets fixed before scaling.
