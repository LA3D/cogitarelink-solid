## Verdict

- **No regressions.** Authoring round-trip and the curator loop both behave exactly as
  their green baselines. Nothing D114 removed (trailer / 422 guard / doc+graph views)
  broke a working behavior.
- **D114's delivery improvement is real.** Governed context (the open action) now reaches

- **But the over-trust problem is NOT fixed — it moved up a layer, from delivery to

  necessary-but-not-sufficient.

## The over-trust trap (Arms 1–2)

Planted: concept `d114-overtrust.md` whose **body** says `[[Progressive Disclosure]]{.broader}`,
plus an open `mem:RealignAction` declaring that link **stale** with the authoritative
broader = Hierarchical Retrieval. Body and `.meta` agree (dual-layer projection); the
correction lives only in the open action (the realistic curator-flagged-but-not-yet-
rewritten case). Question — "what broader topic is Spreading Activation filed under?" —
carried **no staleness cue**. (n=1 per arm; the mechanism is unambiguous, but small sample.)

### Arm 1 — Tier-3 (curl + `solid-pod`), the contract's real tier

- The agent ran `solid-pod read d114-overtrust.md` — the **fused read**. Raw audit
  confirms the tool result **contained `mem:hasOpenAction`** (delivery worked).
- It then answered **"Progressive Disclosure, High confidence."** It never dereferenced
  the open action, never mentioned it, never read the view-authority contract (no
  storage-description / page-profile fetch in the trajectory).
- **Delivery ✅ / interpretation ✗.**

### Arm 2 — curl floor

- Used `curl -i` + a direct `.meta` fetch, so the open action (Link header + `.meta`
  triple) was in context.
- Answered **"Progressive Disclosure, High confidence,"** and explicitly reasoned *"the
  `.meta` was modified today, so it is fresh"* — a false freshness inference; the textbook
  over-trust, worse than Arm 1 (it manufactured confidence).
- **Floor honesty: FAIL** by the criterion "not confidently wrong" — but the cause is the
  same interpretation gap, not a floor-specific defect.

### Why (the diagnosis — corrected after reading the full reasoning narrative)

An earlier draft of this report said the open action was an "opaque pointer the agent
didn't dereference" — i.e. saw-but-didn't-follow. **Reading the actual reasoning turns
(not just the tool calls) shows that is wrong, and the truth is sharper: the open action
never entered the agent's attention at all.** Neither agent mentions `hasOpenAction` /
"open action" / "realign" / "stale" anywhere — reasoning, trajectory writeup, or answer
(zero hits, both runs).

The reasoning shows a **predicate-directed attention** pattern:
- Arm 1, first thought after the fused read: *"The concept has a `skos:broader` link to
  Progressive Disclosure. Let me fetch that resource to confirm."* It locked onto
  `skos:broader`, treated the question as answered, and spent every later call (fetch
  target, wiki-search, SPARQL) **confirming the label** — classic confirmation mode.
- Arm 2: *"The content has the answer... `[[Progressive Disclosure]]{.broader}`... let me
  confirm."* Same; fetched `.meta` ("very clear") without registering `hasOpenAction` in it.

The mechanism: the agent searches for the predicate that answers the question
(`skos:broader`), finds it, and stops. `mem:hasOpenAction` is a **sibling triple on the
same subject** — not connected to `skos:broader` in any way the agent's attention would
traverse — so predicate-directed reading skates straight past it. It is not a
follow-the-pointer failure; it is a **never-registered-it failure**. This is worse than,
and structurally different from, D112 Probe-2 (where the question was at least *whether*
the agent noticed a Link header): here the signal is delivered into the representation and
the agent's attention still never lands on it.

**Design consequence (sharpened):** a back-pointer parked on the resource subject is
structurally invisible to an agent reading for a specific predicate. The qualification
must be **attached to the triple it qualifies** — the agent reading `skos:broader` has to
encounter "⚠ stale per <op>: should be Hierarchical Retrieval" *as part of reading the
broader*, not as a separate triple it has no reason to look at. (This also partly
re-vindicates the D113 trailer, which intercepted linear top-to-bottom body attention with
a ⚠ block; the `.meta` back-pointer intercepts nothing.)

Note the contrast with the (withdrawn) D113 trailer: the trailer **inlined the rationale**
into the body, which is more salient than the opaque `.meta` back-pointer — but it was
markdown-only and smeared metadata. The fused read is content-type-agnostic and clean but
delivers an **opaque pointer**. Neither, as built, makes the agent act.

## What this means

- **Safe to keep / push:** no regression; the substrate stays honest (`make audit` 0
  ERROR throughout); delivery is a genuine improvement over the D112 dead-end.
- **RQ-Substrate-4 read-path: still OPEN.** Delivery was necessary but not sufficient. The
  next gap is **open-action interpretation**: an `mem:hasOpenAction` back-pointer that an
  agent doesn't dereference doesn't change behavior. Candidate directions (next brainstorm,
  not built):
  1. **Attach the staleness to the qualified triple, not a sibling back-pointer** (the
     load-bearing fix per the corrected diagnosis). The agent reading `skos:broader` must
     encounter "⚠ stale per <op>: should be Hierarchical Retrieval" *as part of reading the
     broader* — inline the `mem:rationale` + `mem:stalenessClass` + affected predicate next
     to (or annotating) the governed triple in the fused view, so predicate-directed
     attention cannot skate past it. A `<resource> mem:hasOpenAction <op>` sibling triple is
     structurally invisible to that attention. (Content-type-agnostic re-do of what the
     trailer's body-position rationale-inlining got right.)
  2. **Get the view-authority contract onto the agent's actual path** — agents handed a
     resource URL go straight to it and never read the storage description; the contract is
     deployed but unconsulted. A per-resource `Link rel="profile"` is emitted, but agents
     don't follow it either. Salience of the contract itself is unsolved.
  3. **Teach open-action semantics** (skill/agentGuide): an open `RealignAction` on a
     predicate means "do not treat that predicate as current without checking the op."
- **The eval method worked:** testing the tool tier (not curl-only) + raw-auditing
  trajectories caught that the headline "delivery → behavior" inference does NOT hold —
  exactly the over-claim trap that bit the D113 probe.
